mnesio has one organizing idea: **the event log is the single system of record,
and everything else is a materialized view of it.** Get that, and the rest of
the system follows.

## The event log (system of record)

Every write is an immutable, append-only `Event` on a fjall-backed log
(`FjallEventLog`). Memories, evolutions, invalidations, link updates, outcomes,
learning-curve points — all of it is events. The log is never mutated and never
overwritten; a "change" is a new event that supersedes an old one.

<Aside type="tip" title="Why this matters">
Because the log is append-only and complete, **every index is rebuildable by
replaying it.** That single property is what makes the frontier features
possible: counterfactual replay (Phase 10), time-travel provenance (Phase 15),
and KV cartridges as just-another-view (Phase 12).
</Aside>

## Materialized views

A view is anything that folds the event tail into a queryable structure. Each
implements the `MaterializedView` trait (`apply(&entry)`), so it can be driven
off the live tail *or* rebuilt from scratch by replay:

## Hybrid retrieval

`HybridRetriever` fuses the vector and BM25 signals with **Reciprocal Rank
Fusion**, down-weighting a mock vector signal so lexical results dominate when
embeddings are stand-ins. Each `Hit` carries an explainable `breakdown` so you
can see *why* it ranked where it did. A reranker stage and graph-proximity +
recency/importance signals fold into the fusion.

## The seams (swappable providers)

Every external dependency lives behind a trait, so providers are swappable
without touching the core:

- `LlmClient` — the model (FakeLlmClient, OllamaLlmClient, …)
- `Embedder` — embeddings (MockEmbedder, FastEmbedEmbedder)
- `EventLog` — the log (FjallEventLog)
- `MaterializedView` — any index
- `Retriever` — retrieval strategy
- `Cipher` / `Signer` — crypto (chacha20poly1305 AEAD, ed25519)
- `KvBackend` — the KV tensor backend (fake, GPT-2, candle/Metal GPU)
