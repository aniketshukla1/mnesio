mneme is built in strict sequence: each phase has a hard "done when" criterion,
and every commit obeys [the seven hard rules](/concepts/hard-rules/). Every phase
below is **✅ shipped**, each behind its own "done when".

<Aside type="note">
Phases 0–9 reached parity-plus-wedge. Phases 10–15 are the *unique* bets — each
only possible (or only *safe*) because of mneme's substrate: append-only +
replayable + bi-temporal + the non-bypassable gate.
</Aside>

## Frontier bets (10–15)

The bets a storage-shaped competitor would have to rebuild its foundation to copy.

### Phase 10 — Causal memory ✅
Exploit the replayable log for **counterfactual credit assignment**: re-run
outcome evaluation with a memory masked, measure the delta, and GC by *provable*
zero contribution instead of a time-decay guess. Offline, bounded, never on the
write path.

### Phase 11 — Self-falsifying memory ✅
Re-checkable acceptance probes (`Held | Refuted | Inconclusive`); on `Refuted`,
the memory auto-supersedes via the canonical triple (history kept), no human in
the loop. Belief confidence is *derived* on read, never persisted.

### Phase 12 — Gated KV cartridges ✅
A KV cartridge is just another materialized view of the log, keyed by
`(model_id, quant, rope_config, log_head)` and rebuildable by replay. The four
reconciliations — versioning, gate-before-activation, audit,
erasure-by-recompile — are proven under test + live, and the open-weights tensor
backend is delivered: real **GPT-2** (pretrained + full generative, with real q8
quant) and a modern **Qwen2.5** model in pure Rust *and* on **Metal GPU**
(config-driven 0.5B–7B; f32/f16/bf16). A suite-level **accuracy-parity** eval
(`mneme-bench kveval`) shows the cartridge answers at least as accurately as
per-query text-context retrieval (LOCOMO-mini 90% vs 80%) while answering
**~167–180× faster**, erasure holding — gated in CI. The cartridge store carries
an LRU byte budget for many-cartridge scale, and the candle backend also accepts
Llama-family configs. See [KV cartridges](/guides/kv-cartridges/).

### Phase 13 — Certified skill exchange ✅
A gated artifact is a portable unit of *certified competence*. `export` wraps it
with a canary suite + issuer report into a signed certificate; `import` is *trust
but verify* — verify the signature, **re-run the canaries locally**, then apply
the importer's own gate. The shipped report is never trusted in the decision.

### Phase 14 — Negative memory + dreaming ✅
*Anti-memory*: a bad outcome compiles into a gated suppression rule — committed
only if its re-eval still passes the gate (a canary-breaking suppression is
refused, so anti-memory can't blind the agent). *Dreaming*: a bounded offline
pass prunes provable dead/harmful weight and re-anchors drifted notes to their
parent.

### Phase 15 — Regulator-grade provenance ✅
A read-path capability over the append-only + bi-temporal log:
`snapshot_as_of(T)` reconstructs the live set as the agent knew it at any past
`T`; `provenance(memory)` traces every belief to its source events and
supersessions; a redaction policy applies a crypto-shred uniformly across all
`T` — live reads and historical replays alike — while the log stays append-only.

<Aside type="tip" title="The frontier is complete">
All of Phases 10–15 are shipped behind the seven hard rules, each with a live
"done when" — including Phase 12 (the KV-cartridge moonshot): real open-weights
backends on CPU + GPU, a CI-gated accuracy-parity eval, and erasure-by-recompile.
</Aside>

## What's next (planned)

### Phase 16 — Retrieval parity ◑ in progress
This phase keeps **retrieval** competitive with the 2026 leaders on the hard
LoCoMo / LongMemEval categories by folding two ideas from the
[competitor tracker](https://github.com/mneme/mneme/blob/main/COMPETITORS.md)
into the existing RRF fusion — behind the same seven hard rules. Both components
are **shipped and tested** in `mneme-index`:

- **Content-aware reranker** (`rerank::LexicalReranker`) — a dependency-free,
  cross-encoder-style final stage that re-scores the over-fetched candidate list
  on full text via a `ContentProvider` seam (production wires the BM25 view).
  Four features — query **coverage** (multi-hop), **temporal** date-token match,
  **phrase** bigram overlap, and an **update** cue that surfaces a *superseding*
  memory over its stale original (the knowledge-update case). It blends as a
  *bounded additive bonus* on the normalised base score, so it can promote a
  content-relevant hit past a near-tie but cannot let a weaker retrieval signal
  evict a stronger one — recall@k is protected by construction.
- **Hierarchical Context-Tree traversal** (`context_tree::ContextTree`) —
  organizes memories domain→topic→subtopic from their tags and routes a query to
  the best-covered branch (the ByteRover / OpenViking approach). Routing only
  ever *narrows*, and falls back to the full corpus on any ambiguous query — so
  it can help recall but never hurt it.

**Measured (live, real embedder) — and honestly, a mixed result.** All numbers
below are a *paired* A/B: the corpus is ingested **once** and both arms query the
same index, because evaluating the arms over separately-built indexes lets HNSW's
build randomness dominate the per-category deltas on a 12-memory suite. Repeated
runs, LongMemEval-mini, `fastembed`:

- **recall@1 — a clear win.** 50/50 runs improved overall (+10 to +30pp). The
  **knowledge-update** category goes **0% → 100%**: flat fusion returns the
  *stale* memory ("favourite language was Python") where the update cue surfaces
  the *superseding* one ("now Rust"). Caveat: `preference` regressed in **3/50
  runs (6%)**.
- **recall@3 — not a win.** Over 20 runs: 11 unchanged, 6 improved +10pp, and
  **3 regressed −10pp overall**. At a looser budget the reranker is
  neutral-to-occasionally-harmful on this suite.

So the "done when" is **not met**, and the reranker is deliberately **opt-in**
(`--rerank`) rather than wired into the default server retrieval path. The
residual failure is understood: the unstable question ("dietary restrictions" →
"vegetarian") shares no term with its answer, so it is decided purely by the
vector signal and sits exactly at the `k` cutoff. Remaining work: gate the
reranker on having discriminative signal, then re-measure at k≥3, and find a
corpus with real multi-hop/temporal headroom (both are saturated at 100% on the
mini-suites). Reproduce with:

```bash
cargo run -p mneme-bench --release -- memeval \
  --suite longmemeval --k 1 --embedder fastembed --compare-rerank
```

See [`COMPETITIVE.md`](https://github.com/mneme/mneme) in the repo for the
per-competitor "why they can't copy this" breakdown.
